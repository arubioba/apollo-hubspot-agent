# Global discovery and Google context

Discovery now uses Apollo `POST /mixed_people/api_search` against its global prospect database. `/contacts/search` and `/accounts/search` are read only to build exclusions, never as the prospect source. No contacts, companies, or enrichment jobs are created in Apollo. HubSpot is read only during discovery.

Saved records are read afresh for each run: Apollo contacts/accounts and HubSpot contacts/companies, including pagination. Matching uses Apollo person/organization IDs, available email/LinkedIn, normalized company domains and normalized company names. Corporate email domains on existing HubSpot contacts also exclude that company. Missing permissions, malformed responses, incomplete pagination or provider failures stop discovery. Apollo's 50,000 saved-record display limit and the 100,000-record HubSpot safety cap are explicit blockers, not silently incomplete lists. Duplicate matching is limited to identifiers actually present in provider records; missing or changed identifiers cannot be conclusively matched.

The first 1,000 saved domains are also supplied as Apollo exclusions; all saved names, IDs, and domains remain in the local comparison. Industry uses documented People Search `q_keywords` (keyword relevance, not a guaranteed industry taxonomy). Country means employer headquarters. Explicit contact locations and recognized seniorities are sent separately. Similar titles are disabled. Existing local company exclusions still run where source data is present; absent technology information is not proof of non-use.

People Search does not return email/phone and can obfuscate surnames. Such previews are preserved using Apollo person IDs and nullable email, labeled as requiring enrichment, and cannot be selected for existing email-based HubSpot write flows. No synthetic email or surname is created. Google snippets do not supply missing contact identifiers.

## Serper

Set `SERPER_API_KEY` on the server (Railway service `apollo-hubspot-agent`). It is never returned to the browser. Each accepted prospect makes one `POST https://google.serper.dev/search` request (up to 5 organic sources, at most 3 concurrent requests). This uses the account's Serper quota. Partial contact names use company context only. Results include original snippets, source links, retrieval timestamp, and explicit missing-key/no-result/provider-error status. Sources are unverified snippets, not assertions generated by a model. They are persisted as JSONB and rendered as escaped text with HTTP(S)-only links.

Discovery is bounded at 60 People Search calls and 100 requested prospects. When the search budget is exhausted, the result is labeled partial. Saved-record reads are additional API requests but do not use Apollo enrichment credits. Apollo Organization Search (paid per page) and people enrichment are not called.

## Deployment and validation

Run `npm ci && npm run check`. The tests include PostgreSQL via PGlite to verify upgrading the old NOT NULL email constraint, separate identity storage, repeat upserts, legacy email compatibility and Google context persistence. Production still uses `pg` and the existing database.

The startup migration drops only the email NOT NULL constraint, adds `google_context`, and adds a partial unique index for email-free Apollo identities. No records are deleted. Rolling back the application does not require removing the additive column/index.

Live validation: confirm Apollo key access to People Search, saved contacts and saved accounts; HubSpot contact/company read scopes; and `SERPER_API_KEY`. Run a small ICP and check `apollo.discovery.completed` counts, no matching saved records in results, Google sources, and disabled import on unenriched previews. Do not infer live success from mocked tests.
